# 応募・面接での説明例

以下は確認できたコードと今回の差分に基づく例です。制作時の意図や本人が理解・検証した範囲と一致することを確認してから使用してください。

## 履歴書・ポートフォリオ向け（100〜200文字）

過去にAIでコードを生成した、Python・SeleniumとメールOTP取得を組み合わせたLMSログイン補助アプリを、就職活動に向けてAIツールを活用しレビュー・改善しました。既存機能を維持する方針で責務を分割し、待機の終了条件と認証情報の扱いを見直しました。テストと導入手順も追加しました。実サービスでの認証動作は改修後未検証です。

## 30秒程度の説明

以前AIでコードを生成して作成した、LMSのログインとメールの認証番号入力を補助するPythonアプリです。今回はAIツールのレビュー・実装補助を使い、元の機能を保つ方針で設定・メール・画面操作を分離しました。特に再送で待機が終わらなくなる問題と、認証番号のログ出力を修正し、テストとREADMEを追加しました。実際のLMSでの改修後の動作確認はまだです。

## 「なぜこのように変更したのですか？」

元のコードは短く、処理の流れが分かりやすい一方、設定・メール・画面操作が同じファイルにあり、外部サービスなしで部分的に検証しにくい構成でした。そこで技術スタックや認証フローを変えず、処理の境界に沿って関数を移しました。また、OTP再送で待機時間をゼロに戻すコードは上限を守れないため、再送とは独立した期限に変更しました。AIが提案した修正とテストを使用しています。モックで確認した範囲と実サービスで未確認の範囲は分けて説明しています。

## 技術面接の想定質問と必要な知識

| 質問 | 回答の要点・説明に必要な知識 |
|---|---|
| なぜファイルを分けた？ | 設定・通信・画面操作の変更理由が異なるため。関数単位の分割で十分であり、クラス階層は追加していない。関心の分離と依存関係を説明する。 |
| なぜmonotonicを使う？ | 経過時間の計測に使う。時計の時刻修正と切り離して期限を管理する。再送してもdeadlineを更新しない。同期I/Oでは厳密な全体時間上限にならない点も説明する。 |
| IMAPのUIDとBODY.PEEK[]は？ | UIDでメールを指定し、本文取得で自動既読化させない。採用したメールだけstoreで既読にする。未読状態の副作用と競合の可能性を説明する。 |
| OTPの安全性は十分？ | ログ出力を削除したが、送信元検索は暗号学的な真正性確認ではない。最新の未読でも現在の要求に対応する保証はなく、時刻・要求との関連付けが課題。 |
| パスワードはどこに保存する？ | 新規JSONには保存せずgetpassで入力。既存の平文JSONは互換対応。環境変数も暗号化ではない。将来案のOS資格情報保管庫との差を理解する。 |
| ログイン成功をどう判定する？ | 現状は旧コードのエラー要素不在を継承しており、不十分。認証済み画面の安定した要素や遷移を実サービスで確認する必要がある。 |
| sleepを全部置き換えない理由は？ | パスワード欄とOTP欄が同じIDを使うなど画面依存がある。単に存在を待つだけでは不十分で、遷移・可視性・古い要素の失効を理解して条件を設計する必要がある。 |
| テストは何を保証する？ | 期限が再送で延びない、設定を壊さない、メールを解析できる、例外時に終了することを制御した条件で検証。外部サービスの仕様・実認証は保証しない。 |
| 今回どこをAIが担当した？ | 問題抽出、分割案、修正実装、テスト、文章の草案でAIの関与が大きい。元のログイン・OTP機能もAI生成コードによる過去の制作物。本人が確認できた範囲を具体的に述べる。 |
| Git履歴で何を確認した？ | この作業フォルダには履歴がなかった。元の2ファイルを保存し、SHA-256とgit diff --no-indexで作業前後を比較した。コミット履歴を確認したとは言わない。 |

速度改善率・利用者数・運用実績・完全なセキュリティ保証は測定・確認していないため、説明に追加しないでください。
